# YDV ERP｜整體架構、PWA 平台與分期專案計畫

## 1. 專案願景、使用者與成功邊界

YDV ERP 以鞋廠現場為起點，逐步形成可擴充的 ERP；以**同一套 responsive PWA**支援手機與桌機，不建立兩套獨立產品。手機服務現場查詢、掃碼、回報生產進度與異常提示；桌機服務 Dashboard、搜尋篩選、資料維護與完整管理操作。AI 是各模組的橫向能力，僅在累積可用、可追溯的資料後，逐步提供預警、預測、排程與建議。

本計畫成功的第一個邊界是：「生管於桌機建立製令 → 現場於手機回報完工 → 生管確認完成 → 批次達到可交狀態」。這不等同於採購到出貨，也不代表已完成庫存、物流、成本或全廠 ERP。任何尚未送達伺服器的資料不得顯示為已同步或已完成。

目標使用者為生管、現場操作員、倉儲／物流、採購、管理者與資訊安全管理者；各角色可讀取相同的業務事實，但只能執行其被授權的操作。

## 2. 現況定位與既有可延用邊界

- Git root 是 `YDV/`；`ERP/` 是其中一個獨立前端 prototype，另有 `sole-spec/` 與 `sole-3d-demo/`，三者未形成 monorepo 或共用後端。
- `ERP/` 現用 React 19、TypeScript、Vite、Tailwind CSS 與 Three.js；其 `components/`、`pages/`、`types/`、`mock/`、`services/`、`utils/`、`config/` 分層可作為 UI prototype 的演進起點。
- 現有 `Product`、`ProductionOrder`、`ProductionItem`、`DeliveryBatch` 及 service 邊界是**候選 DTO／介面邊界**，不是既定正式資料模型或 API contract；目前資料是 in-memory Mock Data，重整即遺失。
- 有效 Vault 專案目錄是 `Project/YDV/`，既有文件以 `vault: 專案索引`、`vault: 系統架構`、`vault: 模組/ERP` 與 `vault: 工作進程/2026-09-22-鞋廠生產管理-Prototype` 為準。本文件是該結構下首次正式整體計畫。

## 3. 八大模組、依賴與 AI 切入點

產品、供應商、客戶、倉別、單位、代碼與媒體資產是**共用主檔／代碼能力**，不是第九個業務模組。每個主檔必須有唯一擁有者、穩定 ID、啟停用規則與稽核來源；`sole-spec` 的展示資料在經人工確認前不得直接成為 ERP 主檔。

| 模組 | 唯一責任與主要依賴 | AI 可切入點（資料充分後） |
|---|---|---|
| 生產製造 | 擁有 BOM、製程、製令、工單、排程、完工、成本與交期事實；依賴產品主檔，後續讀採購到料、進銷存帳與倉儲實體事件。 | 延誤預警、產能／交期預測、排程建議。 |
| 採購管理 | 擁有請購、詢價、比價、採購單與供應商承諾；讀生產需求與供應鏈建議，**不直接寫庫存**。 | 供應商交期與價格異常、建議詢比議對象。 |
| 倉儲物流 | 擁有儲位、收料、上架、揀貨、配送、出貨與運輸的實體執行事實；讀採購單、製令與交貨條件。 | 揀貨路徑、裝載與配送異常提醒。 |
| 進銷存管理 | 擁有庫存帳、入出庫、調撥、盤點及其數量／價值記錄；只根據倉儲或生產的已核實事件入帳，不以人工覆寫庫存取代交易。 | 帳實差異、呆滯／缺料預警。 |
| 供應鏈管理 | 擁有跨採購、生產、庫存與交期的計畫、協調、預測與分析；讀交易事實，僅輸出建議與計畫，不覆寫交易。 | 需求預測、缺料／交期風險與跨廠調度建議。 |
| 財務會計 | 擁有帳務、應收應付、分錄、結帳與即時報表；讀已核實的商業交易與成本事實。 | 對帳異常、現金流與成本偏差預警。 |
| 人力資源 | 擁有出勤、薪資、績效、訓練與人員資格；向生產提供經授權的人員／班別能力，但不改寫製令。 | 人力負荷、訓練需求與異常出勤提醒。 |
| 資訊安全 | 擁有帳號／角色／權限、稽核、備份與資安事件；是所有模組的橫向控制面。 | 異常登入、權限濫用與稽核事件偵測。 |

品質（QC）的歸屬尚未定案：可分別由採購、製造與倉儲持有進料、製程與出貨檢驗，或另訂橫向品質邊界；在取得人類決策前，不另開空白品質模組。

## 4. PWA app framework 與技術邊界

第一階段平台骨架只預留可被第一切片實際使用的介面：

- responsive app shell、模組導覽、頁面版型與最小設計 token；桌機與手機採同一 repo、同一 API／DTO、不同 route 群與 route-level code splitting，不把桌機表格硬縮為手機畫面。
- 身分、角色與權限的後端邊界；初始至少區分生管與現場。前端隱藏按鈕不是權限控制。
- 稽核、通知、附件、搜尋、API error format 與主檔代碼的共用介面；未被第一切片使用時不預建假 API、空頁或空資料夾。
- 掃碼、離線儲存、同步佇列與同步狀態的介面位置；後端是唯一的狀態判定、彙總與授權來源。

技術上可延用現有 React／TypeScript／Vite／Tailwind 與 service 邊界；正式切片開始前需補 URL routing、server-state 資料存取、後端發號與 API contract。不得過早導入 Redux、事件溯源、複雜離線資料庫、SSO、CDN／MinIO、OpenAPI codegen、Pact、通用 3D 資產管線或大型 AI 平台。只有在相應的第二個消費者、明確整合契約、離線需求證據或人工核准出現後，才評估該項工具。

## 5. 第一個生產製造垂直切片

### 範圍

- 產品、顏色、製令、批次交貨計畫與完工進度。
- 桌機生管建立／調整製令與批次；手機現場掃碼查詢並回報每批每色的**增量**完工事件；生管確認製令完成。
- 後端持久化、跨裝置一致、穩定 ID 與 URL、後端發號、後端狀態機與兩個最小角色權限。
- 完工事件至少包含 `eventId`、操作人、裝置、掃描值、client／server 時間與增量；後端以 `eventId` 去重並負責加總與不變式驗證。

### 非目標與避免假端到端規則

- 不實作 BOM、工單工序、採購、庫存、收貨、出貨、成本、品質或完整排程；不為它們預留空欄位或假資料。
- 「批次全部完工」只表示可交狀態，不表示已出貨；未實作的採購狀態不可留在第一切片狀態機中假裝流程已串接。
- 不把完工數自動轉為庫存數字，不把 3D Viewer 放在現場回報的關鍵路徑。
- 以 3–5 筆去識別化的真實製令驗收，並讓非開發者完成一次「建立 → 回報 → 完成」流程。

### 驗收條件

1. A 裝置建立製令後，B 裝置重新載入可看見相同資料。
2. 後端強制每色批次計畫總和等於製令色數量、完工不得超過計畫，且由後端產生不可變 ID／單號。
3. 現場回報以 append-only 增量事件儲存；重送相同 `eventId` 不重複計數。
4. 生管與現場角色的讀寫範圍不同，且由後端拒絕未授權請求。
5. 有 API contract test 與一條端到端測試覆蓋建立、回報及確認完成。

## 6. PWA、掃碼、離線與同步 roadmap

| 期別 | 可交付成果 | 明確邊界與觸發條件 |
|---|---|---|
| PWA 第一階段 | 360px 至桌機的 responsive UI、Web App Manifest、可安裝體驗、app shell 快取、清楚網路狀態；手機相機掃碼採連網查詢／提交。 | API 採 NetworkOnly；離線時顯示 banner 並禁用送出。掃碼前必須確認條碼對象、格式、標籤責任與後端不可變 ID；HID 掃碼槍可先驗證流程，相機須有相容性 fallback。大型 3D 資產不預快取。 |
| PWA 第二階段 | 必要資料離線讀取、離線暫存完工事件、順序同步佇列與自動重試；使用者可見同步中／成功／失敗／需處理。 | 僅在現場確有離線需求且第一切片事件模型已上線後做。佇列為 at-least-once，成功才刪除；逾期未同步、裝置遺失與伺服器拒絕均為可見風險。 |
| PWA 第三階段 | 多人／多裝置衝突處理、外部來源與完整離線能力的評估結果。 | 多手機增量事件可加總但超量進待處理；桌機對桌機使用 version／409，不自動合併；桌機對手機由製令 owner 處理待辦。MES、設備、Excel、背景同步、完整離線資料庫與事件流，須先有真實整合需求與資料責任人。 |

## 7. 模組 roadmap 與可驗收成果

1. **平台與生產製造切片**：先滿足第 5 節驗收條件；主檔僅做支援此切片的最小產品／顏色／單位／代碼。
2. **採購管理**：僅在 BOM、請購責任與供應商／詢比議流程確認後啟動；驗收為採購單與供應商承諾可追溯，且收貨不直接由採購改庫存。
3. **倉儲物流與進銷存**：先由倉儲產生收貨、上架、出貨、盤點等實體事件，再由進銷存依事件記帳；驗收為能追溯帳實來源與盤點調整，無人工覆寫庫存。
4. **供應鏈管理**：待上述交易已有足夠歷史資料才建立預測與協調；驗收為建議可追溯至資料來源，且採購／生產仍保有是否採納的決定權。
5. **財務會計與人力資源**：在既有會計、薪資、工時制度與整合方式確認後分別導入；驗收為來源交易、權限與稽核可對帳。
6. **資訊安全與 AI**：資訊安全的最小角色、稽核與備份隨第一切片啟動；SSO 或進階資安只在既有 IdP、合規或使用者規模觸發時評估。AI 僅在資料完整性、責任人與人工覆核規則可驗證後導入。

## 8. 資料邊界與跨模組整合規則

- 採購擁有「向誰、買什麼、多少、何時到」；進銷存擁有數量／價值帳；倉儲物流擁有物件位置與實體移動；供應鏈擁有計畫、協調與建議。
- 模組只能寫自己擁有的資料；跨模組以已核實的事件或單據整合，禁止直接寫對方資料表／聚合。
- 採購讀需求、寫採購單；倉儲依已下採購單收料並產生實體事件；進銷存據此入帳。生產完工產生完工事實，倉儲據此入庫，進銷存再記成品帳。
- 供應鏈只讀交易事實、寫計畫或建議；它可提出建議採購需求，採購才決定是否轉為正式單。
- 手機只產生現場事件，不直接改聚合；桌機可修改聚合並處理待辦；後端是唯一彙總、版本判定、授權與稽核來源。

## 9. 架構決策、風險、交叉討論與待答問題

### 本次共識

Codex 與 Claude Code 在 Herdr 內完成兩輪唯讀交叉討論。共識為：生產製造適合作為第一個切片，但必須是可持久化、跨裝置、具最小角色權限與事件稽核的真實流程；產品主檔是共用基礎；手機與桌機共用資料／API，不能共用相同操作、權限或頁面互動；採購、進銷存、倉儲物流與供應鏈必須維持唯一寫者，供應鏈不覆寫交易。

交叉討論的具體異議已納入本計畫：既有 prototype 中「已全部交貨」不得等同完工、未可達的採購狀態不可列為第一切片流程、手機不可共用桌機編輯權限、完工回報不可維持覆寫欄位模型，且相機不能是唯一掃碼來源。

### 暫定假設與風險

- 暫定採同一套 responsive PWA；是否採 Spring Boot、現場語言、登入／IdP 與外部會計整合均未定案。
- Service worker 可能讓離線使用者誤認資料已送達，故第一階段 API 必須 NetworkOnly 且狀態可見。
- 現有 3D 模型與展示資料有價值，但不構成現場必需流程，也不應主導正式產品主檔或資產平台設計。
- 現有 repository 追蹤了 `node_modules/` 與 `dist/`；是否清理及其 Git 歷史影響屬另一項人類決策，本計畫未執行任何 Git 修改。

### 必須由人類回答

1. 製令的上游是客戶訂單、內部計畫或兩者；第一切片是否需要工單／工序層。
2. 完工、採購與製造的狀態轉換由誰觸發；第一切片的採購意涵應完全移除或保留生管手動旗標。
3. QC 的歸屬與 on-hand 數量的唯一擁有者（帳由進銷存、實體由倉儲如何對帳）。
4. 現場帳號模型、裝置 OS、HID 掃碼槍採購與條碼制度（批次／箱／棧板、格式、列印責任）。
5. 真實離線情境、可容忍的事件遺失與未同步時限，以及衝突待辦的 owner／SLA。
6. 稽核事件保留期、不可刪除要求、備份與資安合規；既有 ERP／會計／MES／Excel 等外部整合範圍。

在上述問題未決前，本計畫是有邊界的 roadmap，不授權實作正式資料模型、外部整合或八大模組功能。
